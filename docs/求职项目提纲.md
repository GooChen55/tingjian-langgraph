# 实习求职项目提纲

## 项目定位

听见是基于已有听书工程整合改造的 Java 全栈与 AI 应用项目。选它作为主项目时，重点展示同一业务里的权限、事务、检索、任务恢复和实际验收，不罗列多个不相干的课程项目。

## 简历描述示例

**听见 · 智能听书与 AI 业务助理**｜Java 17、Spring Boot、Vue 3、FastAPI、LangGraph、MySQL、Redis、RabbitMQ、Nacos、ES、MongoDB、Milvus、Qdrant、Neo4j

- 在听书业务上整合用户、内容、订单与 AI 服务，通过 Java RBAC 和用户绑定会话控制个人业务、管理权限及跨服务访问；前端支持页面内助手、小窗/全屏和办理卡片。
- 实现 LangGraph 售后流程：订单选择、原因收集、草稿核对、显式确认及持久化中断恢复；业务归属、金额和状态由 Java 再次校验，模型不能直接退款或越过人工审核。
- 构建版本化知识导入与检索：MinIO 保存原件，Outbox/RabbitMQ 驱动解析、分块和向量入库，更新失败保留旧版；通过 Milvus、BM25、HyDE、Neo4j 与按需 MCP 联网召回，RRF 和重排后校验逐字引用。
- 实现面向聚合视图的 NL2SQL：ES/Qdrant 三路元数据召回、目录过滤、SQL AST 校验、只读账号和有限修正，澄清任务可重启续接；展示实际 SQL、口径与审计编号。
- 使用事务 Outbox、发布确认、ACK、租约与死信处理索引最终一致性；将 Mongo 进度改为统一集合、唯一复合索引和原子更新；在共享虚拟机使用专属资源并运行隔离验收。

- 扩展多用户个人知识空间：笔记、时间书签与私人文件采用 owner/space/version 隔离；默认本地关键词检索，授权后使用独立 Milvus 索引和模型引用问答，并基于上报播放区间关联笔记生成听书回顾。

根据岗位删到 3–4 条。只有在你能独立解释、修改并复现后，才把对应条目作为个人贡献；不要直接写“从零原创”“生产级”“全量微服务重构”或没有压测依据的性能数字。

## Java 后端岗位重点

1. 一次修改为什么必须同时提交业务记录和 Outbox？数据库提交与 MQ 发送之间有哪些故障窗口？
2. 发布确认与消费者 ACK 分别证明什么？为什么仍可能重复消息？
3. 乱序消息为什么读取当前专辑状态？如何防止下架内容重新进入结果？
4. MySQL 行锁、唯一回执、稳定退款编号分别解决哪些问题？为什么审核通过不代表银行到账？
5. Redis ACL 与前缀约定有什么区别？Mongo 统一集合为什么仍必须带 userId 条件？
6. Nacos 的 namespace、group、service 和实例 metadata 分别怎么避免混用？为什么只运行三服务？

## AI 应用岗位重点

1. 意图路由、工具调用图和售后任务图各自控制什么？哪些结论绝不能由模型决定？
2. 聊天记录、图检查点、任务业务状态有什么区别？为什么不能仅靠历史消息恢复提交？
3. HyDE 为什么不能直接引用？图谱的关系来自哪里？RRF 与重排解决什么不同问题？
4. 资料更新失败怎样保留旧版？如何隔离模型、向量维度和语料版本？
5. 元数据召回为何不能扩大 SQL 权限？字段错误与越权语句为什么使用不同处理策略？
6. 逐字引用校验只能证明引用出自候选资料，不能证明资料正确或语义一定相关。

## 十分钟演示

- 2 分钟：登录、播放样例、恢复进度、助手查进度并展开实际执行步骤。
- 3 分钟：上传自建资料、查看导入节点、问答引用，再更新资料证明新版生效。
- 2 分钟：售后订单卡片、收集原因、刷新恢复与明确确认，管理台展示待审核申请。
- 2 分钟：运营问数，展示元数据召回、SQL、结果及写入/敏感数据拒绝。
- 1 分钟：专辑修改后的 Outbox / RabbitMQ / ES 状态，说明失败重试与专属虚拟机资源。

## 必须如实说明

- 项目是在已有源码上整合改造；贡献范围和来源见能力映射及来源文档。
- 初始化记录规模不等于真实用户、真实可播放音源或上线规模。
- 真实微信支付、云点播和数字人后续配置；当前交易是明确标记的模拟渠道，不产生资金或付费权益。
- 固定样例评测只证明对应契约，不能写作通用准确率。以本轮验收记录为准，不挪用旧版本结果。
